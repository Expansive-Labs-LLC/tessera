## ⚠️ Special Instructions

> This task must integrate with the existing `Expansive-Labs-LLC/github-actions/versioning` composite action. The versioning action uses `cycjimmy/semantic-release-action@v4` with `@semantic-release/changelog` and `@semantic-release/git` plugins. The Tessera repo needs its own `.releaserc.yml` and CI workflows that consume this reusable action.

> **Blender-specific packaging constraint:** The add-on `.zip` must have `blender_manifest.toml` AND `__init__.py` at the root of the archive (not nested under a subdirectory) for Blender Extensions Platform compatibility. For legacy add-on install, the `.zip` needs a single top-level directory.

## Business Context

### Why This Matters
Automated CI/CD is essential for sustainable open-source maintenance and marketplace publication. Every merge to `main` should automatically: run quality checks, determine the next semantic version, build the add-on `.zip`, and publish it as a GitHub Release. This eliminates manual versioning errors and ensures every marketplace upload corresponds to a tagged, tested release.

### Why Now
Must be in place before the first public release. Marketplace listings link to versioned releases. Contributors need CI feedback on PRs.

## Initial Requirements

> ⚠️ **Starting points only.** Orchestrator will expand into full Spec.

### What Needs to Be Built

#### CI Workflow (Pull Requests)
1. **`.github/workflows/ci.yml`** — Triggered on `pull_request` → `main`
   - **Lint job** — `flake8`, `isort --check`, `black --check`, `mypy`
   - **Test job** — `pytest` with `bpy` stub (headless, no GPU required in CI)
   - **Package job** — Trial `.zip` build to validate packaging works
   - Matrix: Python 3.11, 3.12 (Blender 4.2+ ships Python 3.11)

#### Release Workflow (Merge to Main)
2. **`.github/workflows/release.yml`** — Triggered on `push` → `main`
   - **Version step** — Use `Expansive-Labs-LLC/github-actions/versioning@main` (wraps `cycjimmy/semantic-release-action@v4`)
   - **Build step** — Run build script to create versioned `.zip`
   - **Release step** — Attach `.zip` as GitHub Release asset (semantic-release creates the release)

#### Semantic Release Configuration
3. **`.releaserc.yml`** — In Tessera repo root
   - Branch: `main`
   - Tag format: `v${version}` (e.g., `v1.0.0`)
   - Plugins: commit-analyzer, release-notes-generator, changelog, github (attach assets), git (commit back changelog + version files)
   - Assets: `tessera-*.zip`, `CHANGELOG.md`

#### Build Script
4. **`scripts/build_addon.sh`** — Deterministic add-on packaging
   - Accept version as argument (from semantic-release or manual)
   - Patch `bl_info["version"]` tuple in `tessera/__init__.py`
   - Patch `version` field in `blender_manifest.toml`
   - Create `tessera-v{VERSION}.zip` with correct structure:
     - For Blender Extensions: `blender_manifest.toml` + `__init__.py` at zip root
     - Exclude: `tests/`, `__pycache__/`, `.git/`, `.venv/`, `specs/`, `tasks/`, `.agent/`, `.pytest_cache/`
   - Validate the zip contains required files before finishing

#### Blender Extension Manifest
5. **`blender_manifest.toml`** — Required for Blender 4.2+ Extensions Platform
   - Schema version, add-on ID (`tessera`), version, metadata, license, permissions (files + network for model weight download)

#### Supporting Files
6. **`CHANGELOG.md`** — Auto-generated by semantic-release on first release
7. **`.github/dependabot.yml`** — Weekly updates for GitHub Actions dependencies

### Known Constraints
- Semantic-release requires Conventional Commits (enforced via CONTRIBUTING.md from TASK-TS-0012)
- The versioning action is a composite action in `Expansive-Labs-LLC/github-actions` — must reference it correctly cross-repo
- Blender Extensions Platform requires `blender_manifest.toml` + `__init__.py` at zip root — this differs from legacy Blender add-on install which expects a subdirectory
- CI tests must run without a GPU (use `bpy` stubs or mock GPU detection)
- Build script must produce TWO zip variants if both Extensions Platform and legacy install are needed, OR a single zip that works for both (investigate during spec)
- The `.releaserc.yml` in the `github-actions` repo uses `tagFormat: ${version}` (no `v` prefix) — Tessera should use `v${version}` for convention; verify no conflict

### Success Looks Like
A PR triggers lint + test + trial build. A merge to `main` with a `feat:` or `fix:` commit automatically creates a new GitHub Release with a correctly versioned, installable `.zip` artifact. The maintainer can directly upload that `.zip` to marketplace listings.
